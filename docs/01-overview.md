# 01 · 全貌：低延遲交易所由哪些元件組成

## 一張圖看懂

```text
                     ┌──────────────────────── 關鍵路徑（微秒級，全在記憶體） ────────────────────────┐
 會員/客戶端          │                                                                              │
 ──TCP/二進位協定──▶ Gateway ──▶ Sequencer ──▶ Matching Engine（每個商品/分片一條執行緒）──▶ 事件流 ──┼─▶ 回報（Execution Report）回 Gateway
  (OUCH / iLink3 /    │  驗證、限流     定序、寫      確定性狀態機：限價簿 + 撮合規則              │
   ETI / FIX)         │  pre-trade 風控  journal、複製                                                │─▶ 行情發布（UDP multicast：ITCH / MDP3 / EOBI）
                     └──────────────────────────────────────────────────────────────────────────────┘
                                                      │
                                         非關鍵路徑（非同步，毫秒~秒級）
                                                      ▼
                         Drop copy、清算/結算、監視（surveillance）、帳務、歷史資料、報表
```

幾乎所有現代低延遲交易所（Nasdaq INET、CME Globex、Eurex/Xetra T7、LSE Millennium、LMAX、
各大加密交易所的新一代引擎）都收斂到同一組設計原則：

| 原則 | 意思 | 為什麼 |
|---|---|---|
| **單執行緒撮合** | 一個商品（或一組商品）的限價簿只由一條執行緒擁有 | 撮合本質上是循序的（價格-時間優先），加鎖只會變慢；單執行緒沒有鎖、沒有 cache line 爭用、行為可預測 |
| **全部在記憶體** | 熱路徑上不碰磁碟、不碰資料庫 | 一次磁碟 fsync 就是數十微秒到毫秒，比整個撮合慢 100~10000 倍 |
| **確定性 + 事件溯源** | 引擎是純函數：`(狀態, 輸入) → (新狀態, 輸出)`；只持久化「排序後的輸入」 | 當機後重播輸入即可恢復；備援機吃同一份輸入就能同步，不需要分散式交易 |
| **分片（sharding）** | 依商品切分，不同商品在不同核心/機器上平行撮合 | 水平擴充吞吐量；商品之間在熱路徑上幾乎沒有共享狀態 |
| **二進位、固定長度協定** | 對外 OUCH/ITCH/SBE，對內也是 | 解析 FIX 文字或 JSON 是巨大且不穩定的開銷 |
| **熱路徑零配置** | 啟動時預先配置所有物件池、環形佇列 | `malloc`、GC、page fault 都是尾延遲（tail latency）的主要來源 |
| **忙等 + 綁核** | 熱路徑執行緒 busy-spin，綁定在隔離的 CPU 核心 | 執行緒睡眠/喚醒要數微秒，context switch 會把 cache 洗掉 |
| **行情用 UDP multicast** | 一次發送，所有訂閱者同時收到；A/B 雙路備援 + 序號 + 補洞 | 公平（大家同時收到）、低延遲、扇出不增加交易所負擔 |

## 延遲預算（數量級）

以下是「業界常見的數量級」，不是任何特定交易所的保證值：

| 環節 | 典型延遲 |
|---|---|
| 光在光纖中走 1 公尺 | ~5 ns |
| L1 交換器（Arista 7130 / 前 Metamako 類） | ~5 ns |
| cut-through 乙太網路交換器 | ~數百 ns |
| 一般 Linux kernel TCP/UDP 收送（含 syscall、中斷） | ~數 µs 到數十 µs |
| kernel bypass（OpenOnload / ef_vi / DPDK） | ~1 µs 以下到數 µs |
| 跨核心傳遞一則訊息（SPSC ring） | ~數十到數百 ns |
| 撮合一筆委託（記憶體內、cache 熱） | ~數十 ns 到 1 µs |
| `malloc` 命中慢路徑 / minor page fault | ~µs 級 |
| 一次 GC 停頓（未調校的 JVM） | ~ms 級 |
| NVMe `fsync` | ~數十 µs 到 ms |
| 跨機房複製（同城） | ~數百 µs 到 ms |

一個頂級交易所從 gateway 收到委託到送出確認（order-to-ack），內部延遲大致落在 **個位數到數十微秒**；
撮合本身只佔其中一小部分，**網路堆疊、序列化、跨執行緒傳遞、持久化/複製** 才是大頭。
所以「低延遲交易所」的工程重點不是撮合演算法有多聰明，而是 **把撮合以外的一切都移出關鍵路徑或壓到極小**。

## 吞吐量的真正來源

- 一條撮合執行緒在現代 CPU 上可以做到每秒數百萬到上千萬筆指令（本 lab 的原型約 1100 萬筆/秒，見 [06](06-measurement.md)）。
  LMAX 在 2011 年公開的數字是單執行緒每秒 600 萬筆委託。
- 單一熱門商品的訊息量通常遠低於這個上限，所以 **單執行緒不是瓶頸**；
  整個市場的總量（例如美股選擇權 OPRA 合併行情峰值可達每秒數千萬則訊息）靠的是 **分片**。
- 瓶頸往往在：gateway 的連線數與協定解析、行情扇出、持久化/複製的頻寬、以及需要跨商品的風控（保證金、餘額）。

## 一筆委託的生命週期

1. **Gateway**：TCP session（如 SoupBinTCP、FIX session）→ 驗證身分與序號 → 訊息格式檢查 → 限流（每秒訊息數）
   → pre-trade 風控（價格合理性/fat-finger、單筆上限、信用額度、自成交防範設定）→ 轉成內部固定長度二進位格式。
2. **Sequencer**：替訊息蓋上全域（或分片內）單調遞增序號，寫進 journal、送到備援機。**從這一刻起，這筆輸入的處理結果就被確定了**。
3. **Matching Engine**：依序號處理，更新限價簿，產生事件（接受、成交、取消、拒絕）。
4. **輸出**：
   - 回報給下單者（經原 gateway）
   - 行情增量（L2 價量變化 / L3 逐筆委託）發到 multicast
   - Drop copy 給風控部門、清算系統
5. **非同步後處理**：清算、帳務、監視、資料倉儲。
