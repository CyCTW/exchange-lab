# 07 · 傳統交易所架構：設計與模擬

本 lab 的主線先以 **傳統交易所**（證券、期貨）為目標，加密貨幣交易所放到 [08](08-crypto-architecture.md) 之後再深入。
這一章把 [01](01-overview.md)–[05](05-reliability.md) 的原則落實成一個可以跑、可以量、可以驗證的模擬器：
[`src/exchange/`](../src/exchange/)、[`src/bin/exchange.rs`](../src/bin/exchange.rs)。

```bash
cargo run --release --bin exchange -- --gateways 2 --partitions 2 --members 60 --instruments 40 --rate 200000 --secs 5
```

## 1. 為什麼先做傳統交易所：兩者的核心差異

| 面向 | 傳統交易所（本章） | 加密交易所（[08](08-crypto-architecture.md)） |
|---|---|---|
| 參與者 | **會員**（券商、做市商、自營商）數十到數百家，經專線、二進位協定連線 | 數百萬個 **終端用戶**，經公網 REST/WebSocket |
| 風控 | 會員的 **信用額度**、單筆上限、價格合理性，在 gateway **事前** 檢查；交割由結算所事後處理 | 每筆委託前 **精確凍結餘額**，跨商品共享 |
| 順序 | **中央定序器**：所有輸入一個全域序號 → 整個系統可用一份 journal 重播 | 常見各元件各自排序（例如以 Kafka 串接） |
| 交易時段 | 有開收盤：**盤前 → 開盤集合競價 → 連續交易 → 收盤集合競價** | 7×24 連續交易 |
| 商品狀態 | 漲跌幅、盤中暫停、以集合競價恢復 | 通常只有連續交易 |
| 行情 | UDP multicast 的 **逐筆（L3）** 行情，每個分區一個頻道、帶序號 | WebSocket 推播，常做聚合 |

傳統交易所的架構更「純粹」：撮合只看價格與數量，風控在入口就處理完，整個核心是一條被定序的訊息流。
先把這個模型做紮實，之後再看加密交易所為了「即時餘額」與「7×24」要額外付出什麼代價。

## 2. 模擬的市場

| 面向 | 模型 |
|---|---|
| 商品 | 40 檔股票（`--instruments`），參考價 50~1,000 元（tick 0.01 元），**漲跌幅 ±10%**；熱度呈 Zipf 分佈 |
| 會員 | 60 家（`--members`）：**做市商** 1/6（每檔股票兩家做市商，以 **改單** 持續更新雙邊報價）、**自營商** 1/6（連續交易時送 IOC 吃單）、**經紀商** 其餘（代客掛單、撤單、市價；偶有肥手指） |
| 交易日 | 壓縮成 `--secs` 秒：0–15% 盤前、15% **開盤集合競價**、15–85% 連續交易、85–95% 收盤前累積、95% **收盤集合競價**後收盤 |
| 盤中事件 | 45% 時暫停最熱門的股票、50% 時 **以集合競價恢復**；60% 時一家經紀商 **斷線 → 交易所自動撤掉它所有委託**，65% 重新連線 |
| 事前風控 | 每個 session 限流、單筆數量上限 5,000 股、委託價偏離參考價 >7% 拒絕、會員 **信用額度**（未結委託金額上限） |

## 3. 拓樸與執行緒模型

```text
 會員 ─┐
       ▼
 ┌───────────────┐  請求       ┌──────────────┐  依商品路由     ┌───────────────────┐  逐筆行情（每分區一個頻道）  ┌───────────┐
 │ Gateway ×G    │ ─(G SPSC)─▶ │  Sequencer   │ ─(P SPSC)─────▶ │ Partition ×P      │ ─(P SPSC)──────────────────▶ │ MarketData│
 │ ・指派訂單編號  │             │ ・全域序號     │                 │ ・每檔股票一本簿    │                              │ ・重建 L3 簿│
 │ ・限流          │             │ ・時間戳       │ ─(SPSC)─┐       │ ・交易階段/競價     │                              └───────────┘
 │ ・事前風控      │             │ ・插入市場控制 │          ▼       │ ・確定性狀態機      │
 │ ・部位/信用占用 │             └──────────────┘   ┌─────────┐    └───────────────────┘
 └───────────────┘                                  │ Journal │              │
       ▲                                             └─────────┘              │
       └───────────────────────── 執行回報（P×G SPSC）─────────────────────────┘
```

執行緒數 = G + 1（定序器）+ P + 1（行情）+ 1（journal，可關閉）。每個元件只擁有自己的狀態，彼此只透過 SPSC ring 溝通。

### 一筆委託的旅程

```text
經紀商 #23 買 1101 共 500 股 @ 189.50
 1. gateway-1   指派 order_id = 23<<40 | 流水號；限流 ✓；數量 ≤ 5,000 ✓；偏離參考價 ≤ 7% ✓；
                信用：未結 1.2 億 + 9.5 萬 ≤ 額度 ✓ → 占用信用，送往定序器
 2. sequencer   蓋上 seq=418,207、時間戳 → 寫 journal；1101 在 partition-0 → 送往 partition-0
 3. partition-0 連續交易中：撮合 → Accepted、Trade（對手是做市商 #4 的賣單）
                → 回報：Ack（給 #23）、Fill（給 #23）、Fill（給 #4）
                → 行情：Trade、Executed（#4 的賣單減量）；剩餘量掛上簿 → Add
 4. gateway-1   Ack（記錄延遲）；Fill：部位 +300、現金 −300×成交價、釋放對應信用
    gateway-0   Fill：做市商 #4 部位 −300
 5. md          套用 Executed / Add，自己的 1101 簿與撮合簿保持一致
```

## 4. 關鍵設計決策

### 4.1 中央定序器：唯一決定「順序」的地方

定序器替每則請求蓋上全域單調遞增的序號，並依時程插入 **市場控制事件**（進入開盤、收盤、暫停、恢復）。
這些控制事件也拿到序號、也寫進 journal——所以「開盤競價發生在第 N 則訊息之後」是被記錄下來的事實，重播時會在完全相同的位置發生。

撮合分區是 **確定性狀態機**：不讀時鐘（只用定序器蓋的時間戳）、不依賴雜湊表迭代順序（整批撤單時先依編號排序）、所有輸出都經過同一個 `Sink`。
因此 `PartitionCore` 同一份程式碼既跑在即時執行緒上，也能 **離線重播 journal**：

```text
[OK] journal 重播 → 輸出與最終簿完全相同（確定性）  713,881 筆紀錄（45.7 MB），重播耗時 0.31 秒
```

每次執行結束都會重播，比對每個分區所有輸出（回報＋行情）的滾動雜湊與最終簿。這是 [05](05-reliability.md) 中「hot standby 吃同一份輸入就得到同樣狀態」的直接證明。

定序器的代價：它是 **單點、也是吞吐上限**。真實系統會讓定序器極度精簡（只蓋序號、轉發），並以主備或共識協定（Raft）提供容錯。

### 4.2 事前風控在定序之前

Gateway 擋下的委託（限流、數量上限、價格偏離、信用不足）**不會進入 journal**，因此不影響撮合的確定性，也不消耗定序器與撮合的資源。
傳統交易所能這樣做，是因為風控對象是會員的 **信用額度**（粗粒度、可以保守估計）：gateway 在送單時占用信用，收到成交/撤單回報時釋放；
同一筆額度晚一點釋放只會讓會員稍微保守，不會造成錯誤。這和加密交易所必須在撮合前 **精確** 凍結每一分餘額截然不同。

### 4.3 依商品分區，控制事件廣播

每檔股票只屬於一個分區，所以一般委託只送到一個分區；**階段變化、整批撤單、暫停/恢復** 則廣播給所有分區（不負責該商品的分區直接忽略）。
因為每個分區只從定序器的單一佇列讀取，它看到的是全域序列中屬於自己的 **子序列**，順序和全域序號一致。

`--placement balanced`（預設）依熱度把股票分配到最空的分區；在 Zipf 分佈下兩個分區的訊息量約 50.5% / 49.5%。

### 4.4 交易日與集合競價

| 階段 | 簿的行為 |
|---|---|
| 盤前、收盤前累積期、暫停中 | **集合競價模式**：委託只掛上簿、不撮合（簿可以暫時交叉）；IOC 被拒（`InvalidPhase`） |
| 開盤 / 收盤 / 恢復 | **uncross**：在交叉區間內選一個價格，所有可成交的委託都以這個價格成交 |
| 連續交易 | 價格-時間優先即時撮合 |
| 收盤 | 新委託一律拒絕 |

競價價格的選擇規則（`OrderBook::uncross`）：**可成交量最大 → 未成交量最小 → 最接近參考價 → 價格較低**；參考價落在交叉區間內時也列為候選。
成交後簿保證不再交叉（可證明：若仍有交叉，必存在另一個成交量更大的價格）。測試以 300 組隨機委託與暴力解比對。

範例（4 秒交易日）：

| 代號 | 開盤競價 | 暫停後恢復 | 收盤競價 |
|---|---|---|---|
| 1101（最熱門，盤中被暫停） | 189.67 × 181,400 股 | 188.29 × 2,800 股 | 187.96 × 155,700 股 |
| 1108 | 708.78 × 44,000 股 | - | 707.80 × 41,000 股 |

### 4.5 改單（Replace）與訂單編號

訂單編號 = `會員編號 << 40 | 流水號`，任何元件都能直接算出回報要送回哪個 gateway。
改單採 OUCH 的語義：撤掉舊單、以 **新編號** 掛新單、**失去時間優先**；舊單若已不存在（例如剛好被成交），整筆改單以 `UnknownOrder` 拒絕。
做市商的訊息中改單佔大宗（模擬中約 54% 的訊息是改單），其中約 15% 因為報價在途中已被吃掉而被拒——這是真實做市商每天都在面對的「在途競態」。

### 4.6 逐筆行情與驗證

每個分區是一個行情頻道，有自己的連續序號（對應 MoldUDP64 的 session）。事件是 ITCH 風格的 `Add / Executed / Deleted / Trade / AuctionResult / Phase / Halt / Resume`。
行情接收端 **只靠這些事件** 重建每檔股票的完整限價簿（含同價位的優先順序），結束時和撮合分區的簿逐筆比對；同時檢查序號沒有跳號。

### 4.7 循環拓樸的死結規則

`gateway → sequencer → partition → gateway` 是一個環。規則和 [08](08-crypto-architecture.md) 相同：**gateway 送不出請求時，一邊等一邊消化回報**；
其他元件可以單純等待。測試把所有佇列容量設為 4 來驗證。

### 4.8 Journal 與撮合的先後（尚未補上的缺口）

目前 journal 執行緒和撮合分區 **平行** 消費定序後的訊息，撮合不等 journal。當機時，可能有已經撮合並回報、但還沒落盤的訊息。
真實系統必須補上其中一種保證：

1. **撮合等 journal**（LMAX 做法）：分區只處理「journal 已確認」的序號之前的訊息。
2. **輸出等 journal**：撮合照做，但回報與行情要等對應序號落盤（或複製到備援機）後才送出。
3. **複製取代落盤**：定序後的訊息以 multicast 同時送到主、備分區與 journal，至少兩處收到才算提交。

## 5. 實驗結果

環境：4 vCPU 雲端 VM（Intel Xeon @ 2.8GHz），未做 isolcpus 調校。60 會員、40 檔股票、每秒 20 萬個動作的目標速率（實際約 18 萬則訊息/秒，因為收盤後與集合競價期間部分會員不送單），每組 3–4 秒。延遲從「預定送出時間」起算。

### 拓樸 vs 延遲

| 設定 | 執行緒 | 請求→回應 p50 | p90 | p99 | 請求→行情 p50 |
|---|---|---|---|---|---|
| G1 / P1，無 journal，spin + 綁核 | 4 | **2.0 µs** | **7.7 µs** | 1.6 ms | 2.0 µs |
| G1 / P1，有 journal，spin + 綁核 | 5 | 852 µs | 3.7 ms | 6.6 ms | 4.5 ms |
| G1 / P2，無 journal，spin + 綁核 | 5 | 688 µs | 3.5 ms | 5.5 ms | 4.5 ms |
| G2 / P2，有 journal，backoff（預設） | 7 | 156 µs | 3.1 ms | 4.5 ms | 2.0 ms |

- 每條執行緒獨佔一顆核心時，**gateway → 定序器 → 分區 → gateway 三跳往返只要 2 µs**。
- 多一條忙等執行緒（journal 或第二個分區）就超過核心數，p50 惡化數百倍。**核心預算是設計拓樸的第一個限制**；這台 VM 無法展示分區的擴充效果。

### 單一分區的飽和點（G1 / P1，無 journal，spin + 綁核）

| 目標動作/秒 | 實際訊息/秒 | p50 | p90 | p99 |
|---|---|---|---|---|
| 200k | 178k | 2.0 µs | 7.7 µs | 1.6 ms |
| 500k | 415k | 2.0 µs | 156 µs | 18.9 ms |
| 1M | 606k（部分被限流、信用擋下） | 2.2 µs | 623 µs | 9.4 ms |

### 其他觀察

- **事前風控**：4 秒交易日中信用額度擋下約 1.6 萬筆經紀商委託，肥手指（數量 ×1000、價格 ×2）被數量上限與價格偏離檢查擋下，全部沒有進入定序器。
- **重播速度**：單執行緒重播 71 萬筆紀錄只要 0.31 秒（約每秒 230 萬則）——重播比即時快，是快速恢復與建立備援的前提。
- **斷線自動撤單**：一次斷線撤掉該經紀商在所有分區的委託，回報與行情都正確反映。

### 一致性檢查（每次執行結束都會跑）

```text
[OK] 每個請求恰好一個回應
[OK] 部位與現金流守恆（淨部位、淨現金流加總為 0）
[OK] gateway 未結委託 = 撮合簿掛單，信用占用一致
[OK] fill = 2 × 成交 = 2 × 行情成交
[OK] 行情重建的簿 = 撮合簿（逐筆、含優先順序）
[OK] 交易階段依序發生
[OK] journal 重播 → 輸出與最終簿完全相同（確定性）
```

`tests/exchange.rs` 在多種拓樸、極小佇列、嚴格風控設定下驗證這些檢查。

## 6. 尚未實作、下一步

依優先順序：

1. **Journal 與撮合的先後保證**（4.8）——可靠性的基本要求。
2. **Hot standby**：備援分區吃同一份定序流，主分區故障時接手；用「重播雜湊相同」驗證切換正確。
3. **行情快照與晚加入恢復**：定期廣播整本簿 + 對應序號，讓新客戶端先套快照再接增量；模擬封包遺失與補洞。
4. **自成交防範（STP）**、**當日有效單在收盤時失效**、**動態價格帶 / 波動中斷**（成交價偏離太多時自動進入集合競價）。
5. **Drop copy 與結算**：成交副本送到會員後台；收盤後依部位做結算。
6. **真實網路協定**：gateway 對外 SoupBinTCP/OUCH（或 FIX），行情 MoldUDP64/ITCH。
7. 在 ≥ 8 核心的實體機上量測分區的擴充性。

之後再回到 [08](08-crypto-architecture.md)，比較加密交易所需要的改變：即時餘額凍結、7×24 線上快照與升級、合約保證金與強平。
