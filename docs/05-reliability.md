# 05 · 可靠性：定序、journal、複製、行情恢復

交易所不能掉單、不能重複成交，而且要快速從當機中恢復。
低延遲交易所的解法 **不是** 分散式資料庫交易，而是：

> **把撮合做成確定性狀態機，然後只複製「排序後的輸入」。**

## 核心概念：State Machine Replication

```text
              ┌──────────── 已排序的輸入日誌（唯一真相）────────────┐
 Gateways ──▶ │ seq=1 New … │ seq=2 Cancel … │ seq=3 New … │ …   │
              └───────────────────┬────────────────────────────────┘
                                  │（同一份日誌）
             ┌────────────────────┼────────────────────┐
             ▼                    ▼                    ▼
       Primary 撮合         Hot standby 撮合       行情 / 風控 / 稽核
      （回報給客戶）        （狀態完全相同）       （各自重建所需狀態）
```

- 確定性：同樣的輸入序列 ⇒ 同樣的狀態、同樣的輸出（逐位元相同）。
- 所以只需要：**(1) 決定順序，(2) 把順序持久化/複製**。狀態本身不需要寫資料庫。
- 本 lab 的測試 `journal_replay_reproduces_identical_state` 驗證了這件事：把 5 萬筆指令寫入 journal，另一個空的引擎重播後，輸出事件流與簿的指紋完全一致。

### 確定性的陷阱

- 不能在撮合中讀系統時間 → 時間戳由 sequencer 寫在輸入裡。
- 不能依賴雜湊表迭代順序、指標位址、未初始化記憶體。
- 浮點運算要小心（不同編譯選項/CPU 可能不同）→ 價格用整數 tick。
- 程式升級：新舊版本對同一份日誌必須產生相同結果，否則要在日誌中的某個點「切換版本」。

## Sequencer（定序器）

所有輸入在進入撮合前先拿到一個單調遞增序號。常見形態：

1. **嵌在撮合引擎前**（LMAX 風格）：網路執行緒收單 → 放進 ring → journal/複製/撮合消費者依序處理。
2. **獨立的中央 sequencer**（許多交易所與交易公司的「sequencer architecture」）：所有元件把訊息送給 sequencer，sequencer 蓋序號後用 multicast 廣播；每個元件（撮合、風控、行情、稽核）都是吃同一個廣播流的狀態機。這讓新增下游元件變得非常容易。
3. **共識協定**（Aeron Cluster 的 Raft）：leader 定序並複製到多數節點後才「提交」，自動選主。

## Journal：寫什麼、何時落盤

```text
選項 A：每筆 fsync           → 最安全，但每筆多數十 µs~ms，吞吐低
選項 B：group commit         → 累積一批再 fsync，攤平成本，延遲上升一點
選項 C：寫入 page cache       → 程序崩潰不掉資料，機器斷電會掉
選項 D：複製到 N 台機器記憶體  → 「在兩台以上機器的記憶體中」視為持久，磁碟非同步寫
```

低延遲交易所多半選 **D（+ 非同步落盤）**：網路複製到同機房另一台主機只要數 µs（RDMA 或 kernel bypass UDP），遠快於 fsync，而兩台機器同時斷電的機率很低。
需要更強保證時，再加上跨機房（災備中心）的非同步複製。

本 lab 的 `--journal` 選項是選項 C：`BufWriter` 批次寫入 page cache；`JournalWriter::sync()` 提供選項 A/B 所需的 fsync。

**先 journal、再處理（write-ahead）**：只要一筆輸入可能影響對外輸出，它就必須已經被持久化/複製。
LMAX 的 Disruptor 用序號依賴表達「撮合消費者不能超過 journal 消費者與 replicator 消費者」——平行執行，但保證順序。

## 快照（Snapshot）

只有日誌的話，恢復時間會隨日誌長度無限成長。所以定期做快照：

- 傳統交易所：**每天收盤後** 停機做快照、清空日誌，開盤前載入。這是 7×24 市場無法享有的奢侈。
- 7×24（加密交易所、外匯）：
  - 在日誌中插入一個「快照標記」指令，引擎處理到該序號時序列化狀態（可以由 standby 做，primary 不受影響）。
  - 或 fork / copy-on-write 的方式在背景序列化。
- 恢復 = 載入最近快照 + 重播快照序號之後的日誌。

## Failover

- **Hot standby**：備援機持續吃同一份日誌，狀態始終同步；primary 掛掉時，standby 只要確認自己已處理到最後一個已提交序號，就可以接手。
- 關鍵問題是 **誰來判定 primary 掛了、以及避免腦裂（兩台都以為自己是 primary）**。做法：外部仲裁者、共識協定（Raft）、或 fencing（讓舊 primary 無法再寫）。
- 對客戶端：gateway 重新連線後依 session 序號續傳；已經回報過的成交不能重複回報 → 輸出也要有序號，下游以序號去重。

## 行情的可靠性

行情走 UDP multicast，**封包一定會掉**，所以協定層一定有：

1. **每則訊息帶序號**（MoldUDP64、CME MDP3 都是）。
2. **A/B 雙路**：兩條獨立路徑發同樣內容，客戶端取先到者、以序號去重（arbitration）。
3. **補洞**：
   - 小洞：向 retransmission server（TCP/UDP unicast）請求特定序號範圍。
   - 大洞或晚加入：先套 **快照 feed**（定期廣播整本簿 + 對應序號），再從該序號之後接增量。
4. **心跳**：沒有資料時也定期送，讓客戶端分辨「沒有成交」與「連線斷了」。

## 對外介面的可靠性

- 下單 session（SoupBinTCP、FIX session、iLink 3）有雙向序號，斷線重連時補送遺漏的回報。
- **Cancel-on-disconnect**：會員斷線時自動撤掉其掛單（可設定）。
- **Kill switch**：風控或會員可一鍵撤掉某帳戶所有委託並禁止新單。
- **Drop copy**：所有成交的副本送到會員的風控/後台系統，獨立於交易 session。
