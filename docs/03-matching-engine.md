# 03 · 撮合引擎與資料結構

撮合引擎要做的事其實很單純：維護一本限價簿，新委託進來時依規則和對手方掛單配對。
難的是 **在每筆數十奈秒的預算內做完，而且每一筆都一樣快**（尾延遲穩定）。

## 撮合規則：價格-時間優先（FIFO）

1. 買單吃 **最低** 賣價、賣單吃 **最高** 買價（價格優先）。
2. 同一價格，**先到先成交**（時間優先）。
3. 成交價 = 被動方（maker，掛在簿上的那一方）的價格。
4. 吃不完的部分：GTC 掛到簿上；IOC 取消；FOK（全部或全不）則事先檢查能否全部成交。

本 lab 的實作：[`src/orderbook.rs`](../src/orderbook.rs)，並在 [`tests/matching.rs`](../tests/matching.rs) 用一個樸素但明顯正確的實作當 oracle，跑 2 萬筆隨機指令比對每一個輸出事件。

## 操作與頻率

真實市場的訊息組成：**新增與撤單佔絕大多數，成交只佔一小部分**（很多市場撤單/成交比在數十倍以上）。所以資料結構要讓這三件事都快：

| 操作 | 需求 |
|---|---|
| 新增委託到某價格層尾端 | O(1) |
| 依委託編號撤單（可能在隊伍中間） | O(1) |
| 取得最佳價 | O(1) |
| 最佳價層清空時找下一個最佳價 | 盡量 O(1) |
| 依序吃掉某層的委託 | O(1) / 每筆 |

## 價格層：怎麼存？

| 方案 | 找價格層 | 找下一個最佳價 | 優點 | 缺點 |
|---|---|---|---|---|
| 紅黑樹（`std::map`、`BTreeMap`） | O(log n) | O(1)（迭代器） | 通用、價格範圍不限 | 指標追逐、cache miss 多、節點要配置記憶體 |
| 排序陣列（最佳價放尾端） | O(log n) 或線性 | O(1) | 連續記憶體、cache 友善；新委託多半在最佳價附近，插入成本低 | 遠離最佳價的插入要搬移 |
| **以 tick 為索引的陣列** | **O(1)** | 需要掃描 → 用 bitmap 加速 | 最快、沒有配置 | 需要有界的價格範圍；記憶體 = 範圍 × 層大小 |
| 雜湊表 + heap | O(1) | O(log n) | 範圍不限 | heap 刪除麻煩，常數大 |

**本 lab 選 tick 陣列 + 非空層 bitmap**：

```text
價格層陣列（每 tick 一格）       bitmap：每個 bit 表示該層是否非空
idx:  ... 100  101  102  103 ...   word = ...0 1 0 1 1 0...
            │         │    │       最佳賣價層清空 → 從 best+1 開始 trailing_zeros()
            ▼         ▼    ▼       一條指令跳過 64 個空層
          [FIFO]   [FIFO][FIFO]
```

- 股票、期貨通常有漲跌幅限制（價格帶），tick 陣列非常合適。
- 價格範圍很大時（加密貨幣），可以：只為「目前價格 ± N tick」配置陣列並在價格漂移時平移；或用兩層 bitmap（summary bitmap 指出哪些 word 非空）讓搜尋變成近似 O(1)。

## 價格層內的 FIFO：侵入式雙向鏈結串列

```rust
struct Order { id, qty, level: u32, side, prev: u32, next: u32 }  // 連結是 slab 索引，不是指標
struct Level { head: u32, tail: u32, qty: Qty, count: u32 }
```

- `prev/next` 直接放在委託節點裡（侵入式），撤單時已知節點位置 → O(1) 解除連結。
- 用 `u32` 索引而不是 64-bit 指標：節點更小、更多節點能塞進 cache；在 Rust 裡也避開了借用檢查器的問題。
- 每層維護 `qty` 總量，L2 行情可以直接讀，不用加總。

## 委託儲存：slab + free list

```rust
orders: Vec<Order>   // 啟動時 with_capacity(max_orders)
free:   Vec<u32>     // 回收的 slot
```

熱路徑上從不呼叫配置器。釋放的 slot 立刻被重用，也讓工作集維持在少量、溫熱的 cache line 上。

**委託編號 → slot** 的查詢：本 lab 用 `HashMap` + 自訂的快速雜湊（預設的 SipHash 為了抗 HashDoS 太慢）。
更進一步的做法：**由交易所自己指派委託編號**，把 slot 索引（加上一個 generation 計數防止誤用舊編號）直接編進編號裡，查詢就變成一次陣列存取，完全不需要雜湊表。客戶端自訂的 ClOrdID 只在 gateway 對照。

## 為什麼是單執行緒

- 撮合的語義是 **全序**：兩筆委託誰先誰後會改變結果。多執行緒撮合同一本簿，最後還是要用鎖或 CAS 決定順序，等於花更多力氣做同一件事。
- 單執行緒 = 沒有鎖、沒有原子操作、沒有 cache line 在核心之間搬移；**行為可重現**（同樣輸入必得同樣輸出），這是 [05](05-reliability.md) 所有可靠性機制的基礎。
- 擴充靠 **分片**：不同商品給不同執行緒/機器。

撮合函數必須 **確定性**：不能讀系統時間（時間戳要由 sequencer 蓋在輸入上）、不能依賴雜湊表的迭代順序、不能用未初始化的記憶體、不能有隨機數（除非種子來自輸入）。

## 事件輸出：callback 而不是回傳 `Vec`

```rust
pub fn execute(&mut self, cmd: &Command, out: &mut impl FnMut(Event))
```

一筆主動委託可能產生數十筆成交；回傳 `Vec<Event>` 就是一次配置。用 callback（C++ 裡常用模板化的 listener）讓呼叫端決定事件去向——直接寫進輸出 ring buffer，零配置、可內聯。

## 其他真實交易所需要、但本原型未實作的功能

| 功能 | 實作要點 |
|---|---|
| 改單（cancel/replace、modify） | 只減量通常 **保留** 時間優先；改價或加量則 **失去** 優先（等同撤單再新增） |
| 市價單、FOK、Post-only | FOK 要先「試算」可成交量；Post-only 若會成交則拒絕或調價 |
| 冰山單（iceberg） | 只顯示部分數量，顯示量吃完後補量並 **重新排到隊尾** |
| 停損單（stop） | 另一本「觸發簿」，依最新成交價觸發後轉成市價/限價單，注意連鎖觸發 |
| 自成交防範（STP） | 同一帳戶/群組的買賣單即將互撮時，依設定取消新單、舊單或兩者 |
| 集合競價（開盤/收盤/熔斷後） | 累積委託，找出「成交量最大、未成交量最小」的單一價格一次撮合（uncross） |
| 價格保護 | 漲跌幅、動態價格帶、熔斷（如美股 LULD），超出時拒單或暫停交易 |
| Pro-rata 分配 | 依掛單量比例分配，處理捨入餘量，可能有 top-order 優先 |
| 組合/價差商品 | 價差單可能與各腿的單一商品簿「隱含撮合」（implied matching），是跨分片狀態的難點 |

## 寫出快的程式碼：幾個習慣

- **資料結構小而緊湊**：常用欄位放同一條 cache line；`u32` 索引代替指標。
- **避免指標追逐**：連續陣列 > 鏈結串列 > 樹。
- **分支可預測**：熱路徑的錯誤處理放在冷函數（Rust `#[cold]`、C++ `[[unlikely]]`）。
- **不要在熱路徑做 I/O、log 格式化、配置記憶體**；log 只寫二進位到 ring，由另一條執行緒格式化。
- **量測再最佳化**：`perf stat` 看 cache miss / branch miss，`perf record` 找熱點。
