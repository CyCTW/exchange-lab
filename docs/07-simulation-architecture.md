# 07 · 多用戶、多商品的交易所模擬與架構設計

前幾章的原型只有「一本簿、一個下單來源」。真實交易所要面對的是：

- **成千上萬個用戶**，類型差異很大：少數做市商貢獻大部分訊息量，大量散戶偶爾下單。
- **很多商品**，熱度極不平均：少數熱門商品吃掉大部分流量。
- **帳戶餘額** 是跨商品共享的：同一個用戶用同一筆 USDT 同時在 BTC/USDT 和 ETH/USDT 下單。
- 限流、餘額不足、撤單時訂單已成交……各種「不快樂路徑」。

這一章把這些需求變成一個可以跑、可以量、可以驗證的模擬器：[`src/sim/`](../src/sim/)、[`src/bin/sim.rs`](../src/bin/sim.rs)。

```bash
cargo run --release --bin sim -- --gateways 2 --risk 2 --matchers 2 --users 10000 --symbols 8 --rate 200000 --secs 5
```

## 1. 模擬的市場

| 面向 | 模型 |
|---|---|
| 市場型態 | 現貨（spot），全部以 USDT 計價：`BTC/USDT`、`ETH/USDT`…（`--symbols`） |
| 商品熱度 | Zipf 分佈（`--zipf`，預設 s=1）：8 個商品時 BTC 約佔 37%，最冷門的約 5% |
| 用戶（`--users`） | **做市商** 約 1%：雙邊報價、不斷撤單重掛，資金雄厚，依商品熱度分配到各商品；**散戶** 約 89%：掛被動限價單、偶爾撤單，資金有限；**主動吃單者** 約 10%：送穿價 IOC |
| 動作比例 | 60% 做市商撤單重掛（一次動作 = 撤單 + 新單兩則訊息）、30% 散戶、10% 吃單 |
| 價格 | 每個商品一條共享的「公允價」隨機漫步（每毫秒一步），所有用戶依它報價 |
| 限流 | 每個用戶一個 token bucket：做市商 5,000 則/秒、其他用戶 100 則/秒（`--mm-limit`、`--user-limit`） |
| 帳戶 | 每個用戶持有 USDT 與各基礎幣；下單先凍結資金，成交後結算，取消後解凍。沒有手續費（因此資產總量守恆，可用來驗證正確性） |

## 2. 拓樸與執行緒模型

```text
                 ┌───────────── 執行回報（R×G SPSC）─────────────┐
                 ▼                                                 │
  ┌───────────────────┐  請求      ┌─────────────────────┐  已凍結資金的委託   ┌──────────────────────┐   成交/最佳價   ┌──────────┐
  │ Gateway ×G        │ ─(G×R)───▶ │ Risk ×R             │ ──(R×M)──────────▶ │ Matcher ×M           │ ──(M×1)───────▶ │ MarketData│
  │ 依用戶分（u % G）   │            │ 依用戶分片（u % R）   │                    │ 依商品分片（placement）│                 └──────────┘
  │ ・模擬用戶行為      │            │ ・擁有餘額            │ ◀──(M×R)────────── │ ・擁有限價簿           │
  │ ・指派訂單編號      │            │ ・凍結 / 結算 / 解凍   │    結算回饋          │ ・不知道任何餘額       │
  │ ・每用戶限流        │            │ ・產生執行回報        │  （成交、取消、拒絕）  │                      │
  └───────────────────┘            └─────────────────────┘                    └──────────────────────┘
```

- 每個方框是一條（或 N 條）執行緒，**狀態只屬於擁有它的執行緒**，沒有任何鎖或共享可變狀態。
- 每一對有通訊的執行緒之間各有一條 **專屬的 SPSC ring**（因此是 G×R、R×M… 的矩陣）。SPSC 是最便宜的跨核心通道，也保證 **每一對之間 FIFO**——後面的正確性推理全都依賴這一點。
- 執行緒數 = G + R + M + 1。

### 為什麼有兩個分片維度

| 元件 | 分片鍵 | 原因 |
|---|---|---|
| 撮合 | **商品** | 限價簿只跟商品有關；同一商品的所有委託必須在同一條執行緒上全序處理 |
| 風控/帳戶 | **用戶** | 餘額跟用戶有關；同一用戶的所有委託（不論商品）必須看到一致的餘額 |

兩個維度是正交的：一筆 BTC/USDT 成交可能牽涉 risk-0 的 taker 和 risk-1 的 maker。這就是 **加密交易所比傳統交易所多出來的難題**——傳統交易所的會員信用額度通常在 gateway 做粗略控管、事後由結算所處理，不需要在每筆委託上即時、精確地鎖定餘額。

### 一筆委託的旅程

```text
New BTC/USDT 買 2 @ 59,430（用戶 4242）
 1. gateway-0       指派 order_id = 4242<<24 | seq，扣 token，送往 risk(4242 % R)
 2. risk-0          檢查 USDT 可用 ≥ 59,430×2 → 凍結 → 送往 matcher(placement[BTC])
 3. matcher-0       撮合：Accepted、Trade(maker=用戶 77 的單, 59,424×2)
                    → Ack、Fill(taker) 送 risk-0；Fill(maker) 送 risk(77 % R)；Trade、Top 送 md
 4. risk-0          Ack → 回報 gateway；Fill：凍結 −118,860，退回價差 (59,430−59,424)×2，BTC +2
    risk-1          Fill(maker)：BTC 凍結 −2，USDT +118,848
 5. gateway-0       收到 Ack（記錄延遲）、Fill（leaves=0 → 從用戶掛單清單移除）
```

## 3. 關鍵設計決策

### 3.1 訂單編號內含用戶編號

`order_id = user_id << 24 | 用戶流水號`。任何元件拿到訂單編號就能算出它屬於哪個用戶、要送去哪個風控分片、回報要送回哪個 gateway——**完全不用查表**，撮合簿也不用多存一個 user 欄位。真實交易所的做法類似：內部編號由交易所指派，客戶自己的 ClOrdID 只在 gateway 對照。

### 3.2 兩階段資金處理：先凍結、後結算

1. **下單前凍結（pre-hold）**：買單凍結 `限價 × 數量` 的 USDT，賣單凍結 `數量` 的基礎幣。不夠就直接在風控拒絕，不會進到撮合。
2. **成交後結算**：買方以限價凍結、以成交價付款，**價差退回可用餘額**；賣方解凍基礎幣、收到 USDT。
3. **結束時解凍**：撤單或 IOC 剩餘量的凍結金額全部退回。

撮合引擎因此完全不需要知道餘額，維持單純、快速。開源的 Java 撮合引擎 [exchange-core](https://github.com/exchange-core/exchange-core) 也是同樣的切法（R1 凍結 → 撮合 → R2 結算，風控依用戶分片、撮合依商品分片）。

### 3.3 循環拓樸與死結

`risk → matcher → risk` 是一個 **環**。所有 ring 都是有界的，如果兩邊都用「滿了就忙等」：

```text
risk-0：  送委託給 matcher-0，ring 滿 → 等 matcher-0 消化
matcher-0：送結算給 risk-0，ring 滿 → 等 risk-0 消化     ⇒ 兩邊永遠互等（死結）
```

`gateway ↔ risk` 也是同樣的環。本模擬的規則：

> **在環上，往下游送不出去時，一邊等一邊消化從下游回來的訊息。**

- risk 送不出委託時，持續處理 matcher 回來的結算（`RiskShard::send_to_matcher`）。
- gateway 送不出請求時，持續處理執行回報（`Gateway::push`）。
- matcher、送回報的 risk 則可以單純等待，因為對方保證會消化。

測試 `heavy_throttling_and_tiny_queues` 把 ring 容量設成 **4**，故意讓背壓不斷發生，以此驗證不會死結。

另一種常見做法是 **讓回饋路徑不經過有界佇列**（例如 LMAX/exchange-core 讓所有階段共用同一個環形緩衝區、以序號依賴推進，結果直接寫回同一個 slot），環就不存在了。

### 3.4 關機協定：用標記訊息排乾管線

`Shutdown` 標記沿著拓樸傳遞：gateway 送完 → 每個 risk 收齊 G 個標記 → 轉給所有 matcher → 每個 matcher 收齊 R 個 → 轉給所有 risk 與 md → 每個 risk 收齊 M 個 → 轉給所有 gateway。
因為 **每一對之間是 FIFO**，收到某個上游的標記就代表它之前送的訊息都已收到。這和分散式快照的 Chandy–Lamport 標記是同一個想法，也是「做快照時如何讓所有元件停在一致的切面」的基礎。

### 3.5 每個請求恰好一個回應

| 請求 | 唯一的回應（在哪裡產生） |
|---|---|
| 新單 | `Rejected(餘額不足)`（risk）、`Rejected(價格帶/簿滿/重複)`（matcher）、或 `Ack`（matcher） |
| 撤單 | `CancelRejected`（risk 找不到，或 matcher 找不到 → 已成交）或 `Done`（matcher） |

其他回報（Fill、IOC 剩餘量取消）是「非請求的」主動通知。gateway 依此量測 **請求 → 回應** 的往返延遲，最後也驗證 `請求數 == 回應數`。

### 3.6 商品放置（placement）與熱門商品

依 Zipf 分佈，`modulo` 放置（商品 i → 分片 i % M）會讓 BTC、SOL、XRP、DOGE 落在同一個分片：

| 放置策略 | matcher-0 | matcher-1 |
|---|---|---|
| `modulo` | **61.3%**（BTC SOL XRP DOGE） | 38.7% |
| `balanced`（依熱度貪婪分配） | 49.0%（BTC XRP DOGE） | 51.0% |

**單一熱門商品無法再切分**：BTC/USDT 一本簿只能在一條執行緒上。所以熱門商品的單執行緒效能決定了整個交易所的上限，這也是為什麼撮合核心要極致最佳化，而不是指望水平擴充。實務上的對策：熱門商品獨佔一個分片（甚至獨佔一台機器）、冷門商品打包在一起，並依實際流量定期重新分配。

### 3.7 執行緒數 vs 核心數

每條熱路徑執行緒都在忙等。執行緒數多於核心數時，忙等的執行緒會搶走真正有工作的執行緒的 CPU，延遲會暴增，見下方實驗。所以設計拓樸時，**先算核心預算**。`--idle backoff`（先忙等、再 yield、再短暫 sleep）可以讓超額配置時還能運作，代價是喚醒延遲。

## 4. 兩種排序模型的取捨

本模擬沒有全域 sequencer：每個元件按「當下從各個 ring 讀到的順序」處理。這和 [05](05-reliability.md) 描述的全域定序模型不同：

| | **全域 sequencer**（Nasdaq、LMAX、exchange-core） | **元件各自定序**（本模擬，以及許多以 Kafka 串接的加密交易所） |
|---|---|---|
| 順序 | 所有輸入一個全域序號 | 每個元件的輸入順序取決於執行時機 |
| 確定性 / 重播 | 整個系統用一份 log 重播 | 每個元件要 **各自** journal 自己實際處理的輸入順序，才能重播 |
| 跨分片一致性 | 容易推理（所有元件看到相同順序） | 需要像 3.2 那樣的協定（凍結/結算）來保證正確 |
| 擴充性 | sequencer 是單點、也是吞吐上限 | 沒有單一瓶頸，可以各自擴充 |
| 延遲 | 多一跳（經過 sequencer） | 路徑較短 |

兩者都在業界使用。本模擬選後者是為了直接呈現跨分片的資金問題；要把它改成可重播的系統，最小的改動是 **讓每個 risk 與 matcher 分片把自己處理的輸入依序寫進各自的 journal**（[05](05-reliability.md) 的作法套用到每個元件）。

## 5. 實驗結果

環境：4 vCPU 雲端 VM（Intel Xeon @ 2.8GHz），未做 isolcpus 調校。10,000 用戶、8 商品、每秒 20 萬個動作（約 31 萬則訊息），每組跑 3 秒。延遲從「預定送出時間」起算。

### 拓樸 vs 延遲

| 拓樸（G/R/M） | 執行緒 | idle | 請求→回應 p50 | p90 | p99 | 請求→行情 p50 |
|---|---|---|---|---|---|---|
| 1/1/1，綁核 | 4 | spin | **2.0 µs** | **3.3 µs** | 0.75 ms | 2.4 µs |
| 1/1/2，綁核 | 5 | spin | 655 µs | 3.5 ms | 6.0 ms | 4.2 ms |
| 2/2/2 | 7 | backoff | 20.5 µs | 2.0 ms | 4.1 ms | 852 µs |

- **4 跳往返只要 2 µs**（gateway → risk → matcher → risk → gateway，每跳一次跨核心）——前提是每條執行緒都獨佔一顆核心。
- **多一條忙等執行緒（5 條擠 4 核心），p50 從 2 µs 惡化到 655 µs**，比 4 跳的實際工作量慢了 300 倍。這台機器上分片越多反而越慢，這不代表分片沒用，而是核心預算不夠。
- p99 到毫秒級，主因是 VM 與 OS 的干擾（見 [04](04-system-tuning.md)、[06](06-measurement.md)）。

### 單一分片的飽和點（1/1/1，spin，綁核，每組 2 秒）

| 目標動作/秒 | 實際訊息/秒 | 被限流的動作 | p50 | p90 | p99 |
|---|---|---|---|---|---|
| 500k | 712k | 66k | 2.0 µs | 3.1 µs | 1.0 ms |
| 1M | 919k | 651k | 2.2 µs | 18 µs | 4.1 ms |
| 2M | 1.23M | 2.03M | 2.3 µs | 197 µs | 12 ms |

- 目標速率越高，**限流** 擋下的比例越大——做市商每秒 5,000 則的上限就是保護撮合核心的第一道防線。真實交易所一定在 gateway 限流，不讓單一會員灌爆系統。
- 單一分片在約每秒 100 萬則訊息時開始排隊（p90 上升），而純撮合本身每秒可處理約 1,100 萬筆（[06](06-measurement.md)）。**瓶頸是風控與跨核心傳遞**：每則請求平均產生約 1.3 則結算回饋，再加上一次執行回報。

### 一致性檢查（每次執行結束都會跑）

```text
[OK] 資產守恆（每種資產 可用+凍結 總量不變）
[OK] 凍結金額與未成交訂單一致、無負餘額
[OK] 每個請求恰好一個回應
[OK] 風控未結訂單 = 撮合簿掛單
[OK] fill = 2 × 成交 = 2 × 行情成交
```

只要任何一條訊息在執行緒之間遺失、重複或處理錯誤，這些檢查就會失敗。`tests/sim.rs` 在多種拓樸與極小佇列下都會驗證這些檢查。

## 6. 尚未模擬、但真實交易所需要的

- **可重播性**：每個分片的輸入 journal + 快照（見第 4 節）。
- **主備切換**：每個分片的 hot standby。
- **手續費、maker/taker 費率**（加入後資產守恆檢查要納入手續費帳戶）。
- **合約交易**：保證金、未實現損益、強制平倉——風控從「凍結餘額」變成「即時計算整個帳戶的風險」，跨商品的耦合更強。
- **真實網路**：gateway 對外用 TCP、二進位協定；行情用 UDP multicast 加序號補洞。
- **自成交防範、價格保護帶的動態調整、熔斷、集合競價**。
- **熱點重新分配**：執行期間把商品從一個分片搬到另一個（需要暫停該商品、移交簿的快照）。

## 7. 下一步建議

1. 在 ≥ 8 核心的實體機上，用 spin + 綁核跑 2/2/2、2/2/4，觀察分片的實際擴充效果。
2. 為 risk、matcher 分片加入輸入 journal，寫測試驗證「重播後餘額與簿完全一致」。
3. 讓 risk 送委託、matcher 送結算時批次處理，量測吞吐提升。
4. 加入合約與保證金，觀察跨商品風控對延遲的影響。
